## Top 3 Learnings

### 1. Dual-path voice-agent architecture for low-latency structured capture *(Technical / Architecture — pitagentsV2)*
The auto-repair-shop OS rebuild settled on a two-task agent split that decouples responsiveness from data accuracy: **Task A** is a direct-address detector (~100ms) that decides whether the user is talking *to* the agent, and **Task B** is a fire-and-forget extraction loop that accrues structured quote data in the background. Paired with a "single **Generate Quote** action, no draft preview — the live form *is* the running preview" UI decision, this avoids the round-trip latency that draft/confirm flows impose on voice UX. Shipped as a clean backend foundation: **all 17 tasks merged to main, 41/41 tests passing**, `feat/backend-foundation` merged and deleted. Other load-bearing choices: Pipecat voice layer + FastAPI backend (Approach B), multi-shop `shop_id` scoping from day one, pluggable external-tool providers (Mitchell1 / Epicor / NHTSA), and pgvector seeded-but-unused so session history can be added later without a migration.

### 2. `pipecat-ai` PyPI version trap — verify availability before pinning *(Tool/Workflow — surfaced independently in pitagentsV2 AND language-learning)*
Both Pipecat projects hit the same wall the same day: **the latest `pipecat-ai` published on PyPI is `0.0.36`; pinning a higher constraint like `>=0.0.47` fails because that version doesn't exist yet.** language-learning resolved it by relaxing the constraint to `>=0.0.36` (all needed integrations — daily, deepgram, cartesia, silero — are present in 0.0.36). Worth flagging an ecosystem-naming wrinkle: the yc-hackathon submission references "Pipecat 1.3.0," which is a different version line/packaging than the `pipecat-ai` 0.0.x PyPI series — easy to conflate when scaffolding a new repo. **Rule:** check the actual PyPI release page before writing a Pipecat version constraint.

### 3. SQLite-as-agent-state conventions, validated via tests-first *(Process / Technical — language-learning)*
The English-tutor backend established a reusable pattern for storing agent state in SQLite: enable `PRAGMA foreign_keys = ON` (SQLite leaves FK enforcement **off by default**), use the `sqlite3.Row` factory for dict-like row access, make id columns `TEXT PRIMARY KEY` for UUID compatibility, and store nested per-learner state (`skills_progress`, `to_review`, `up_next`, `practiced`, `mistakes`, `mastered`) as JSON in `TEXT` columns parsed on read. Schema is idempotent (`CREATE TABLE IF NOT EXISTS`) and was built TDD-style — failing tests written first, then `schema.py` to make them pass (`de3e333`, 2/2 green).
